# Generated verification hardening qualification

This guide covers the local supporting evidence added by M1152–M1160, M1202–M1211, M1212–M1221, M1222–M1231, and M1232–M1241 for generated Firefox/Chromium build verification. It is **supporting/preflight evidence only**. Issue #10 remains the authoritative exact-head Chromium + Firefox runtime qualification gate, and none of the checks below are browser passes.

## Scope

The generated extension verifier compares reviewed repository inputs with the unpacked `dist/chromium` and `dist/firefox` trees after the generated membership contract and artifact audit have admitted the tree. Direct builds run that verifier before build success is accepted.

The hardened boundary requires:

- direct `tools/build.mjs` execution runs `verifyBuiltExtensionsContent(root)` after final source re-fingerprinting and source/contract semantic re-audits but before reporting build success;
- verifier failure during direct build remains inside the partial-`dist/` invalidation path;
- generated-verifier public entry points accept only exact `chromium` or `firefox` targets and require one non-empty real non-symlink repository root;
- browser generated-member contracts are snapshotted once into frozen verifier-local arrays, capped at **4,096 members**, dense, canonical, duplicate-free, and deterministically ordered;
- before verifier contract values are consumed, the source array is admitted through bounded `Reflect.ownKeys`/own-descriptor inspection: only an own data `length` plus exact dense canonical numeric indices are allowed, values must be primitive strings, and symbols, extra keys, holes, accessors, malformed indices, or oversized membership fail closed;
- generated-tree allowlists are likewise snapshotted once into immutable module-load file/directory membership so one tree audit cannot observe changing contract membership mid-traversal;
- before any generated allowlist path is consumed, the browser contract source is admitted through bounded own-key/own-descriptor inspection: only `length` plus exact dense canonical numeric indices are permitted, entry values must be primitive-string own data fields, and symbols, extra keys, holes, accessors, malformed indices, or oversized membership fail closed;
- generated-tree file/directory membership is retained as immutable sorted arrays and checked with deterministic code-unit binary search rather than retained mutable `Set` state;
- generated path and directory-entry text must be primitive, well-formed NFC Unicode and reject C0/C1, zero-width/BOM, and bidi control text before path normalization or allowlist use;
- verifier source, generated-member, and `dist/<browser>` child paths likewise require well-formed NFC Unicode without control/invisible text and pass one canonical repository-relative forward-slash boundary capped at **1,024 UTF-8 bytes**; absolute, backslash, NUL, empty, dot, dot-dot, escaping, and normalization-alias forms fail closed;
- verifier build-info descriptor mapping first calls canonical `snapshotBuildFingerprintInputs`; only the bounded canonical frozen `{path, bytes, sha256}` snapshot can define the map used by generated-source membership and provenance checks;
- source and list members are read through opened-handle identity-safe bounded I/O rather than unbounded pathname reads;
- every expected copied `src/`/`lists/` member must match its verification build-info descriptor by canonical path, byte length, and SHA-256 before it can define expected generated bytes;
- raw `manifests/<browser>.json` source bytes are capped at **256 KiB**, must match the same build-info descriptor before interpretation, and then require strict UTF-8 plus valid JSON before deterministic generated-manifest formatting;
- before expected-byte construction, each browser proves that `manifests/<browser>.json` and every copied contract source exist in the build-info descriptor map;
- expected generated-member construction rechecks frozen contract cardinality, refuses duplicate expected paths, admits only Buffer values through the aggregate byte gate, and requires final map cardinality to equal the frozen contract;
- expected copied-source and manifest reads snapshot the real non-symlink repository/source-parent ancestry before I/O and revalidate it afterward before descriptor acceptance;
- generated output members are read through identity-safe bounded I/O and each actual member read revalidates browser-root/output-parent ancestry before byte comparison;
- one copied source or generated member is capped at **16 MiB** before allocation, while expected and actual generated bytes are each independently capped at **64 MiB per browser** in aggregate;
- generated `manifest.json` and `build-info.json` remain deterministic explicit transformations;
- after each browser's expected/actual comparisons complete, build-info is recreated and must serialize identically to the source snapshot used for that browser pass;
- after the stable generated-verification pass itself finishes, build-info is recreated again and must still serialize identically before browser verification may return success;
- paired Chromium/Firefox verification creates one canonical build-info snapshot and uses that exact snapshot for both browser expectations; both results must match its source fingerprint and a final cross-browser build-info recreation must remain identical;
- standalone single-browser verification remains source-snapshotted and receives the same final source-state rechecks;
- each browser verification pass starts from a real non-symlink `dist/<browser>` root, records its identity, and uses a confined single-child ancestry sentinel;
- root size must be a non-negative safe integer, root mtime/ctime values must be finite and non-negative, and device/inode identity is retained only when represented as safe integers;
- pass `rootIdentity` is an exact frozen own-data object with validated size/time/device/inode fields; accessors, extra fields, mutable descriptors, and malformed metadata fail closed;
- top-level pass fields are exact frozen enumerable own-data fields and the frozen ancestry state must be rooted at the exact `distDirectory` carried by the same pass;
- pass ancestry is bounded to **64 entries**, must be a dense frozen array with no extra fields, and each ancestry entry is an exact frozen own-data object with canonical path and validated size/time/device/inode metadata;
- immediately before ancestry revalidation, the output root is re-lstat'd and must match the start-of-pass identity; after ancestry revalidation, it is re-lstat'd again and must still match the same identity;
- the canonical generated-tree audit runs once before member verification and again after member comparison/final source re-fingerprint but before the stable output-root pass finishes;
- the generated-tree root is snapshotted before recursive traversal and revalidated after traversal plus required-member validation;
- each visited generated directory is snapshotted before bounded enumeration and revalidated after enumeration and again after descendant processing completes;
- each visited generated entry is classified from fresh `lstat` metadata, so symlinks and non-file/non-directory types fail closed;
- generated traversal admits at most **4,096 entries** and **4,096 directories** globally, each directory may retain at most **4,096 entries**, generated paths are capped at **1,024 UTF-8 bytes**, and stored diagnostics are capped at **128 violations**;
- generated traversal and result ordering use direct code-unit comparison rather than locale-sensitive collation;
- the frozen generated-tree allowlist and frozen generated-verifier contract must agree exactly for each browser in member count, deterministic order, path text, and UTF-8 byte identity under the same **4,096-member / 1,024-byte-per-path** ceilings;
- the only permitted cross-browser generated contract delta is Firefox-only `rules/static.json`: Chromium must exclude it, Firefox must contain it exactly once, and removing it from Firefox must leave the exact Chromium contract;
- each successful browser verification result is a frozen object with exact browser identity, a frozen bounded canonical file array, and a canonical lowercase **64-character SHA-256** source fingerprint;
- paired verification accepts only frozen canonical Chromium/Firefox child results whose fingerprints exactly equal the shared canonical SHA-256 fingerprint, then returns one frozen pair result;
- result/contract audit code is source-only and exposes no network, telemetry, analytics, observation-history, or profile-storage surface.

## Exact-head use

For a candidate intended for real qualification:

1. Use the exact source head from which the Chromium ZIP and Firefox XPI will be produced.
2. Run the canonical preflight/package/release workflow documented in `ROADMAP.md`.
3. Confirm direct build success occurs only after canonical generated verification and that both generated browser trees bind to the same source snapshot/fingerprint.
4. Confirm verifier target/root admission, descriptor-safe frozen generated contracts, descriptor-safe immutable generated-tree allowlists, immutable sorted tree membership, strict Unicode/path confinement, expected-member cardinality, stable output-root/pass identity, bounded deterministic traversal, per-directory/subtree/root identity revalidation, and final generated-tree re-audit remain present on that exact head.
5. Confirm verifier build-info mapping comes only from `snapshotBuildFingerprintInputs`, the verification pass ancestry is rooted at the exact admitted output root, and both pre/post ancestry root identity checks plus the post-pass source re-fingerprint remain in place.
6. Confirm the generated-tree and verifier contract snapshots match exactly for each browser, with `rules/static.json` as the only Firefox-only member.
7. Confirm browser result objects and their file arrays are frozen, result paths are canonical/bounded, fingerprints are lowercase 64-character SHA-256 hex, and the paired result fingerprint equals both browser result fingerprints.
8. Treat any generated source/member/tree/verifier-provenance, contract/admission, browser-delta, result-publication, fingerprint, path, pass-identity, root-metadata, allowlist/membership, or traversal boundary change as invalidating prior supporting evidence for that head.
9. Perform and record the actual Chromium and Firefox observations through the Issue #10 qualification workflow; do not carry browser results forward across a changed exact head.

A successful static/local verification pass is not a Chromium or Firefox runtime pass. It proves only that the local generated candidates match the reviewed exact source snapshot under the documented filesystem, byte-budget, provenance, transformation, path, contract, identity, result, and traversal boundaries.

## Privacy boundary

Generated verification inspects only local repository inputs, generated candidate files, and filesystem metadata necessary to validate those files. It must not retain telemetry, analytics, browsing/request history, page or DOM snapshots, blocked-request/action outcomes, action/accessibility names, consent context, statistics, timestamps, user/device identifiers, locale/profile state, credentials, or owned Drop Ads backend data.
